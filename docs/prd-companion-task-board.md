# PRD：AI 搭子的任务板与技能库

## 0. 文档信息

| 项 | 内容 |
|---|---|
| 状态 | P1 已实现（插件任务板 + Mod HUD），待实机验收 |
| 范围 | 任务板（P1）、RAG 上下文（P2）、技能库（P3）、反应层与记忆（P4） |
| 主入口 | DSH 插件（装完即用，零配置） |
| 游戏内形态 | SMAPI Mod 常驻 HUD 任务条（左上角，无需按键） |
| 关联文档 | `docs/game-native-semantic-architecture.md`、`docs/agent-l4-orchestration-planstate-design.md`、`eval/LIVE-RESULTS.md` |

## 1. 背景

现在玩家对 AI 的体验是“一问一答”：说一句，它做一个动作，做完就结束。它没有“事”的概念，也无法跨回合记住玩家布置过什么。`PlanState` 只是单次对话内的步骤队列，重启即丢，而且保存的是 `tool + args`，不是“玩家的目标”。

调研同类系统后，结论很一致（详见 §13）：

- Voyager 的能力增长来自**技能库**（可检索、可组合、可复用），不是更长的 prompt；
- JARVIS-1 的关键是**计划 + 经历记忆**，计划交给快控制器执行；
- Cradle 用“高层规划 → 低层代码”把 LLM 移出实时回路；
- Stardew 的 MCP 实践直接写明：实时战斗要原生自动，因为“LLM 往返太慢”。

所以本 PRD 不做“更大的 prompt”，而是补三样东西：**任务板（记得住）、技能库（做得成）、验证与反应（做得对）**。

## 2. 目标与非目标

### 目标

1. 玩家装一个 DSH 插件就能用，不需要 Python、不需要改配置；
2. 玩家用自然语言布置任务，AI 能理解意图并落成结构化任务，写入持久化的任务板；
3. 任务在游戏内可见：左上角常驻任务条，随时看到当前任务与进度；
4. 任务可查看、可修改、可取消、可跨会话继续；
5. 任务完成由**世界状态**判定，而不是模型自述；
6. 任务执行时能拿到“刚好够用”的上下文：游戏规则、相关技能、历史经验；
7. 逐步支持“组合已有原子能力形成新技能”，并复用。

### 非目标

- 不做通用 agent 框架，所有概念贴着星露谷；
- 不追求全自动游玩，玩家始终可以打断、修改、取消；
- 不在 P1 做技能自动生成（需要沙箱与安全设计，放 P3）；
- 不在 P1 做实时战斗/钓鱼的 LLM 控制（放 P4，且用原生兜底）；
- HUD 任务条 P1 只做“看”，不做“点”（取消/暂停仍在聊天里完成）。

## 3. 用户与场景

**核心用户**：正在玩星露谷、愿意把一部分重复劳动交给 AI 的玩家。

| 场景 | 玩家说 | 期望 |
|---|---|---|
| 一次性任务 | “帮我把这块地清了” | 建任务、执行、报告结果 |
| 有数量/期限 | “春天结束前攒 5000 金” | 任务带截止条件，跨天推进 |
| 组合目标 | “砍点木头做 20 个箱子” | 理解“箱子要木头”，拆成采集 + 制作 |
| 查询 | “我现在还有什么没做完？” | 读出任务板 |
| 修改 | “算了，先别砍了” | 暂停/取消，不丢已完成部分 |
| 干涉 | “先别干了，跟我去镇上” | 优先级抢占，任务挂起 |

## 4. 产品形态

玩家看到三样东西，其中任务列表**在游戏里**：

1. **建任务时的确认**：聊天里一句人话复述，例如“好，目标：木头 ×120，用来做 20 个箱子。现在开始？”
2. **游戏内常驻任务条（HUD）**：屏幕左上角一条半透明小条，默认显示：
   - 当前任务：状态点 + 标题 + 进度（`砍木头 48/120`）；
   - 队列：`还有 2 个任务`（或第二行显示下一个任务）；
   - 卡住时整行变黄并显示原因（体力不足 / 天黑了 / 缺工具）；
   - 没有任务时不显示；
   - 位置、透明度、显示行数、开关都在 Mod 配置里；
   - 不接收鼠标/键盘输入，不暂停游戏，打开菜单或节日时自动隐藏。
3. **阶段反馈**：开始、卡住（附原因）、完成，各一句聊天消息。

聊天里的 `任务` / `进度` 仍然可用，作为任务条的文本备份。

## 5. 功能需求

### FR-0 零配置接入

- 玩家只做一件事：在 DSH 里添加插件；
- 插件自动探测游戏、SMAPI、Mod 版本；缺 Mod 时沿用现有安装流程（原生确认后下载）；
- 不要求玩家安装 Python、配置环境变量、或手动改 JSON；
- HUD 任务条依赖的 Mod 版本在安装时校验，版本不够就提示升级。

验收：全新机器，装插件 → 进游戏 → 能建任务、左上角能看到任务条，中途不需要命令行。

### FR-9 游戏内常驻任务条（P1）

- 形态：`OnRenderedHUD` 事件里绘制的常驻小条，不是弹窗菜单，不需要按键；
- 默认位置：屏幕左上角（时钟在右上角，避免遮挡），可配置偏移；
- 显示内容：当前任务一行（状态点 + 标题 + 进度），可选第二行显示队列数量；
- 最多 3 行，超出只显示“还有 N 个任务”；
- 状态颜色：进行中（绿）、排队（灰）、卡住（黄）、完成（白，显示 3 秒后消失）；
- 背景半透明，文字用 `Game1.smallFont`；中文依赖游戏语言字体，需在 zh-CN 下实测；
- 自动隐藏：`Game1.activeClickableMenu != null`、节日/事件、切场景加载中；
- 不注册输入事件，不拦截点击；开关与布局全部走 Mod 配置；
- 数据来源：插件通过本地路由同步快照（见 FR-10）；
- 没有 Mod 或版本过旧时，插件只在聊天里提供列表，不报错。

验收：建 3 个任务（1 进行中、1 排队、1 卡住）→ 进入游戏左上角常驻显示；打开背包时自动隐藏；关闭背包恢复；中文与英文都不溢出。

### FR-10 任务板同步（插件 ↔ Mod）

- 插件是任务板的唯一数据源；Mod 只做展示缓存；
- 同步时机：任务变更、进入游戏、重连、定时（30s 兜底）；
- 消息：`local_task_board`（local_direct 帧），载荷为精简快照（id、标题、状态、进度文本、阻塞原因、revision）；
- Mod 按 `revision` 去重，旧 revision 丢弃；
- 断线时 Mod 继续显示最后一次快照，并标注“离线”；
- 不传敏感信息（不传玩家 id、不传完整 goal）。

验收：断线重连后任务条在 2s 内恢复；revision 乱序不会回退显示。

### FR-1 意图识别与任务抽取

输入玩家一句话，输出结构化意图：

```json
{
  "intent": "assign",
  "tasks": [
    {
      "title": "做 20 个箱子",
      "goal": { "type": "craft", "item": "Chest", "qty": 20 },
      "derived": [{ "type": "acquire", "item": "Wood", "qty": 120 }],
      "constraints": ["不卖工具", "不熬过 2 点"],
      "priority": "normal"
    }
  ],
  "clarify": null
}
```

`intent` 取值：`assign` / `query` / `cancel` / `modify` / `chat`。

验收：

- 缺数量、缺对象、指代不明时返回 `clarify`，不猜；
- 同一句话重复说不会产生重复任务（幂等）；
- 派生需求（配方）来自 RAG（P2），P1 允许先用固定规则。

### FR-2 任务板持久化

- 每个存档（save id + 玩家 id）一份任务板；
- 进程重启、DSH 重启后任务仍在；
- 原子写入，损坏时回退到上一个快照；
- 任务状态：`proposed → confirmed → active → blocked / paused → done / failed / cancelled`。

验收：建任务 → 重启 DSH → `任务` 仍能读出。

### FR-3 任务执行驱动

- 同一时刻只有一个 `active` 任务；
- 高优先级任务可抢占，被抢占的置 `paused` 并记录断点；
- 每次工具调用结果回写任务 `progress` 与 `evidence`；
- 卡住时写 `blocked_reason`（体力/时间/缺工具/不可达/需要玩家决定）。

验收：一个长任务执行中插入新指令，原任务挂起而不是丢失。

### FR-4 完成判定（关键）

每个任务必须带 `completion` 谓词，由世界事实求值：

```json
{
  "completion": {
    "type": "inventory_at_least",
    "item": "Chest",
    "qty": 20
  }
}
```

支持的谓词（P1）：`inventory_at_least`、`gold_at_least`、`crops_watered_all`、`day_advanced`、`manual_confirm`（确实无法自动判定的，显式标注并请玩家确认）。

验收：模型声称完成但谓词不成立 → 任务保持 `active`，并记录一次 `false_completion` 指标。

### FR-5 上下文装配

每次决策注入的上下文按预算裁剪，顺序固定：

1. 当前任务 + 子目标 + 约束（最高优先，不裁剪）；
2. 世界快照摘要（时间、体力、位置、背包关键项、天气）；
3. 相关技能/知识卡片（P2 起由 RAG 提供，最多 3 条）；
4. 最近 2 条失败或阻塞记录；
5. 任务板摘要（其余任务的标题与状态）。

验收：单次请求 prompt 增量 ≤ 1200 tokens（P1 目标）；超出时先裁第 5 项，再裁第 4 项。

### FR-6 任务操作

- `任务`：列出现有任务（最多 8 条，长清单折叠）；
- `继续`：恢复 `paused` 任务；
- `取消`：置 `cancelled`，保留记录；
- `改`：修改数量/期限/优先级，重新计算 `derived`。

验收：每个操作都有自然语言确认，且不误删已完成部分。

### FR-7 RAG 上下文（P2）

- **K0 结构化表**：作物日历、配方、价格、掉落表、NPC 喜好，SQLite；
- **K1 技能/知识卡**：每个能力与常见组合的“怎么做、常见坑”；
- **K2 散文 wiki**：现有 2.7MB，混合检索；
- 检索触发：建任务时（配方/需求）、执行前（条件）、失败后（原因）；
- 每条注入内容带来源，便于复盘。

验收：说“做 20 个箱子”能推出木头数量并说明依据（“每个箱子 6 木”）。

### FR-8 技能库（P3）

- 允许把多个原子调用组合成一个**命名技能**（参数化），存入技能库；
- 按描述检索（先用关键词 + 向量混合，不追求复杂）；
- 执行前做静态校验（只用白名单能力、参数范围、无危险调用）；
- 技能有版本与最近成功率。

验收：一个新组合技能被创建后，下次同类任务能直接检索并复用。

## 6. 数据模型

```json
{
  "schema_version": 1,
  "save_id": "farm_abc",
  "player_id": "u_123",
  "tasks": [
    {
      "id": "task_01H...",
      "title": "做 20 个箱子",
      "source": "player",
      "goal": { "type": "craft", "item": "Chest", "qty": 20 },
      "derived": [{ "type": "acquire", "item": "Wood", "qty": 120 }],
      "completion": { "type": "inventory_at_least", "item": "Chest", "qty": 20 },
      "constraints": ["不卖工具"],
      "priority": 5,
      "deadline": { "day": 28, "season": "spring", "year": 1 },
      "status": "active",
      "progress": { "wood": 48, "chests": 0 },
      "display": { "progress_text": "木头 48/120", "status_text": "进行中" },
      "subtasks": [],
      "evidence": ["chop_trees wood_gained=48"],
      "blocked_reason": null,
      "created_at": "2026-10-26T21:00:00+08:00",
      "updated_at": "2026-10-26T21:20:00+08:00"
    }
  ],
  "archived": []
}
```

存储位置：插件进程写入 `~/.starcoplay/tasks/<player_unique_id>.json`（原子写、损坏留档）；后续 agent 侧复用同一 schema。

## 7. 架构与集成

```
玩家话术
  → 意图抽取（LLM, 结构化 JSON）
  → 任务板（持久化，DSH 插件进程内）
  → 上下文装配（任务 + 世界 + RAG + 记忆）
  → 决策（DSH 模型）
  → 工具调用（现有 starcoplay_* / 后续 skill）
  → 结果回写（progress / evidence / blocked_reason）
  → 完成判定（谓词求值）
  → 同步快照（task_board_sync）
  → Mod HUD 任务条（只读展示，断线保留最后快照）
```

P1 落在 DSH 插件（TypeScript），因为那是玩家当前真正在用的入口，且不依赖 Python 运行时。同一个 schema 留给 agent 侧复用；P3 再评估是否收敛到单一任务服务。

游戏内任务条的最小实现：

- Mod 在 `OnRenderedHUD` 里绘制（`Game1.smallFont` + 半透明底），默认锚点左上角 `(16, 16)`；
- 收到 `task_board_sync` 后存内存，按 `revision` 取最新快照；
- 只读，不注册输入；`Game1.activeClickableMenu != null` 或节日时跳过绘制；
- 文本走 i18n，标题过长截断并显示省略号；
- 配置项：`HudEnabled`、`HudOffsetX/Y`、`HudOpacity`、`HudMaxLines`。

## 8. 非功能需求

| 项 | 要求 |
|---|---|
| 延迟 | 任务操作（增删改查）< 50ms；意图抽取 p95 < 2.5s；任务板同步 < 200ms |
| 成本 | 建任务单次 ≤ 1500 tokens；上下文增量 ≤ 1200 tokens |
| 可靠性 | 任务板原子写；损坏可回退；重启不丢；任务条断线显示最后快照 |
| 安全 | 任务只能调用白名单能力；危险动作（卖工具、拆建筑）需确认；同步不传敏感字段 |
| 可观测 | 每次任务状态变化写本地日志，含原因 |
| 游戏内 | 任务条不接收输入、不遮挡时钟/体力/快捷栏；位置与透明度可配置；不掉帧 |

## 9. 指标

| 指标 | 定义 | 目标（P1） |
|---|---|---|
| 任务捕获率 | 玩家布置任务被正确建单的比例 | ≥ 85% |
| 澄清率 | 需要追问的比例 | ≤ 20% |
| 完成率 | 建单后 3 个游戏日内完成 | ≥ 70% |
| 假完成率 | 声称完成但谓词不成立 | ≤ 5% |
| 平均 tokens/任务 | 建单 + 执行上下文 | ≤ 4k |
| 恢复率 | 重启后任务可继续 | 100% |

## 10. 里程碑

| 阶段 | 内容 | 验收 |
|---|---|---|
| P1 | **一次性发布**：插件任务板（意图抽取、持久化、列表/取消/继续、完成谓词、上下文注入）+ Mod HUD 任务条（`task_board_sync`、i18n、版本校验、新 Mod 发布） | 真实存档跑通 5 个任务；重启不丢；左上角任务条状态与进度正确 |
| P2 | RAG：K0 结构化表 + K1 知识卡 + 检索触发 | “20 个箱子”能自动推木头数量 |
| P3 | 技能库：组合、存储、检索、校验 | 新技能可复用，成功率可统计 |
| P4 | 反应层与记忆：原生战斗/钓鱼兜底、失败经验 | 打断后可恢复，不重复踩坑 |

## 11. 风险与开放问题

**风险**

- **任务膨胀**：玩家随口一句话都建单，任务板变垃圾场 → 需要“确认后建单”与自动归档；
- **假完成**：谓词覆盖不到的任务容易自报完成 → 优先只支持可验证任务，其余标 `manual_confirm`；
- **上下文成本**：任务板 + RAG + 世界快照容易超预算 → 固定裁剪顺序；
- **双入口不一致**：DSH 与 agent 各有一套状态 → 先用同一 schema，P3 再收敛；
- **版本耦合**：任务条依赖新版 Mod，插件安装流程要能识别旧版并降级为纯聊天；
- **HUD 遮挡**：常驻显示可能挡住画面 → 默认放左上角、半透明、打开菜单自动隐藏，位置可配置；
- **中文字体**：自定义文本依赖游戏语言字体，需在 zh-CN 下实测，英文环境不能溢出。

**开放问题**

1. 任务板放 DSH 插件还是 agent 服务？（P1 选前者，P3 复议）
2. HUD 默认显示 1 行还是 2 行？是否需要“鼠标悬停展开完整列表”（P2 起）？
3. 多人联机时任务归属谁的存档？
4. 技能库的“写技能”用 DSL 还是受限 Python？安全边界怎么定？
5. 完成的任务在 HUD 上停留 3 秒是否足够，还是只在聊天里提示？

## 12. 安装与发布流程

目标：一个没有技术背景的玩家，只需要“添加插件”。

1. 玩家在 DSH 里添加插件（一条命令或图形入口）；
2. 插件启动时检测：游戏路径、SMAPI 版本、StarCoPlay Mod 版本；
3. 缺 SMAPI → 给出官网链接与一句话说明，不自动装；
4. 缺 Mod 或版本过低 → 走现有安装确认弹窗，下载 `StarCoPlay.zip` 并解压；
5. 安装完成后提示“重进游戏生效”，并说明左上角任务条默认开启、可在 Mod 配置里关闭或移动；
6. 所有失败都落到一句话原因 + 一个“复制诊断信息”按钮，不让玩家看日志。

发布依赖：

- Mod 版本号随任务条上线递增（例如 2.6.0 → 2.7.0），`mod-latest` release 重新上传；
- 插件在握手时校验 Mod 版本，低于最低版本时降级为纯聊天模式；
- 插件与 Mod 的兼容矩阵写进 README。
